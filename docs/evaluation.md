# 如何评估这个 RAG 应用

## 已有验证

`tests/` 是不需要 API 密钥、不会请求外部模型的回归测试。它验证检索融合和数据一致性，不代表真实语义检索或回答质量。

覆盖范围：原问题去重、扩展查询证据进入最终上下文、跨查询排序融合、重复片段去重、重复入库替换、保留其他文档向量、持久化重载、链接参数规范化、空查询和切分边界。

## 可复现的手动演示

1. 配置 DashScope 和 LLM，在“文档沉淀”中依次上传 `examples/learning_notes.txt` 和 `examples/project_notes.txt`。
2. 提问：**“如何把课程复盘与动手做项目结合起来？”** 建议参考片段数设为 4。
3. 检查答案是否同时使用“复盘三个步骤”和“最小项目、记录反馈”等证据。
4. 提问：**“示例材料介绍了哪些数据库性能优化方法？”** 检查系统是否说明材料不足，而不是编造材料中的结论。
5. 再次上传同一份文件，检查文档数和文本块数不会因为重复上传而增长。

以上是人工编写的演示资料和检查步骤，仓库没有附带伪造的模型输出或效果指标。

## 下一步质量评估

建立独立的小型标注集，每条记录包含：问题、相关文档 ID、证据原文或 chunk ID、期望要点、是否应拒答。分别覆盖单文档事实、多文档综合、容易混淆的归属和知识库外问题。

| 维度 | 应如何测量 |
| --- | --- |
| 文档命中率 | Top-k 是否包含标注的相关文档 |
| 证据召回率 | 被召回的标注证据数 / 标注证据总数 |
| 答案忠实度 | 逐项核对答案主张是否受实际上下文支持 |
| 无答案处理 | 无依据问题中正确说明材料不足的比例 |
| 延迟与成本 | 分别记录扩展、Embedding、检索、生成的耗时及 token 用量 |

LLM 评审必须看到**实际送入生成模型的证据全文**，并辅以人工抽查。来源标题本身不能证明答案忠实度；同一个模型自评也不能替代独立验证。

比较基线时固定语料、问题、模型配置和上下文预算，对比“单查询”与“多查询 + RRF”，同时报告召回、延迟和费用。当前尚未提供这类量化对比，因此 README 不宣称精度提升比例。
